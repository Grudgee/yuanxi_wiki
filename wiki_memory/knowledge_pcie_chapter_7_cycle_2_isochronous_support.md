# 等时服务目标

等时服务面向视频、音频、实时控制等需要固定时间间隔传输的流量。普通 QoS 只提供相对优先级，而等时服务还要满足带宽下限、最大延迟、周期性和抖动约束。它要求 Device Core、驱动、Isochronous Broker、VC/端口仲裁、交换机、Root Complex、流控和电源管理共同工作。

# 时间规划与 TBWRR

- PCIe 通过 Time-Based Weighted Round Robin（TBWRR）端口仲裁把时间划分为可预期的时隙；等时流量在其服务窗口获得端口机会，普通流量在剩余窗口竞争。
- 时间规划必须考虑端到端路径上的每个端口、链路宽度、Payload 大小、TLP/DLLP 开销、Credit 和传播延迟。
- 时隙设计目标不是让每个包立即发送，而是保证周期内累计服务量足以满足应用数据率，并限制最坏等待时间。
- 若任一中间 Switch 端口没有相同的服务能力，端到端等时保证会被最弱节点限制。

# 软件支持

## Device Driver

设备驱动需要向等时管理软件报告流的带宽、包大小、周期、延迟和方向等要求，并把获得的 TC/VC 或服务配置写入设备。驱动还必须处理流开始/停止、缓冲水位、错误恢复和热插拔变化。

## Isochronous Broker

Isochronous Broker 汇总多个设备的需求，检查链路和端口是否有足够带宽、VC、Buffer 和仲裁时隙，再决定是否准入新流。它需要协调 Endpoint、Switch 和 Root Complex 的配置，避免局部可行但全路径不可行。

# 拓扑中各组件的协同

- Endpoint 产生/消费实时流，并报告所需带宽、周期和最大延迟；其 VC 和发送队列必须按协议分配。
- Switch 为每个相关下行/上行端口建立 TC/VC 映射和 TBWRR 表，保证流在穿越多个端口时获得足够的时间份额。
- Root Complex 负责系统级仲裁、内存路径和软件协调；其内部资源也可能是瓶颈，不能只验证外部 Switch。
- VC 仲裁只能在有足够 Flow Control Credit 时发送；因此等时配置必须同时留出 Header/Data Credit，并处理 Credit 更新延迟。

# 电源管理影响

进入低功耗状态可提高整体能效，但链路退出延迟会侵蚀等时服务预算。系统必须在流量活跃期间避免不合适的 L1/更深电源状态，或把唤醒延迟计入时间规划。设备、Switch 和 RC 的电源策略需要一致，否则某一节点的唤醒时间可能造成丢包或超时。

# 错误处理影响

Ack/Nak、LCRC 错误和 TLP 重放会增加延迟；错误处理必须保留足够重试预算，不能让重放无限占用等时窗口。若链路持续错误，软件应降低服务等级、停止流或采取降级路径，而不是继续宣称已满足保证。

# 关联与验证

- 端到端验证应测量带宽下限、最大等待、周期抖动、VC Credit 枯竭、Switch 多级累积延迟、错误重放和低功耗退出。
- TC 值不变但 TC/VC 映射可逐链路变化；验证必须检查整条路径而不是只读 Endpoint Header。
